# Toolora 项目开发需求 V1

## 一、项目概述

项目名称：**Toolora**

项目定位：一个免费、简洁、美观、可持续扩展的在线工具集合平台。

目标是整合图片处理、开发者工具、PDF 工具、文本处理、数据转换等实用功能。

用户无需注册登录，打开网页即可使用。尽可能在浏览器本地完成计算，不上传用户文件。

项目代码托管在 GitHub，采用纯静态部署，不依赖传统服务器。

### 核心目标

1. 打造视觉精致、体验流畅的工具网站。
2. 支持持续增加工具，未来可能扩展至数十乃至上百个。
3. 所有工具拥有独立页面，同时保持统一的视觉设计。
4. 支持搜索引擎收录，通过 SEO 获取自然流量。
5. 优先使用成熟的开源库实现功能，避免重复开发底层算法。
6. 尽可能保持零后端、低维护成本。
7. 同时支持桌面端和移动端。

## 二、技术栈

| 模块 | 技术方案 |
|---|---|
| 核心框架 | Next.js App Router |
| 开发语言 | TypeScript |
| 样式方案 | Tailwind CSS |
| UI 组件 | shadcn/ui |
| 图标 | Lucide React |
| 动画 | Motion（按需使用） |
| 状态管理 | Zustand（按需使用） |
| 代码编辑器 | Monaco Editor |
| 本地持久化 | localStorage / IndexedDB |
| 后台计算 | Web Workers |
| 包管理 | pnpm |
| 代码托管 | GitHub |
| 网站部署 | Cloudflare Pages |

使用当前稳定且相互兼容的依赖版本。

项目必须支持 `output: "export"`，最终生成可直接部署的静态文件。

不使用需要持续运行的 Node.js 服务器的功能。

初期不引入数据库、用户登录、付费系统、服务端 API 或管理后台。

## 三、UI/UX 设计要求

**以已经确认的第二版 ToolHub 设计图为主要视觉参考。**

整体定位是专业、美观、实用的在线工具平台，而不是 SaaS 营销宣传页。

### 视觉风格

- 浅色主题优先，支持深色模式。
- 白色或极浅灰背景。
- 蓝紫色作为品牌主色调。
- 工具分类采用柔和的辅助色。
- 使用精致、统一的 Lucide 图标。
- 卡片使用适当圆角、轻边框和柔和阴影。
- 排版紧凑但不拥挤，信息层级清晰。
- 适量使用渐变和动画，不要过度装饰。
- 整体质感参考成熟的现代 Web 工具产品。

不要设计成纯粹的大卡片列表，也不要做成充满 3D 插画的产品宣传首页。

### 页面结构

**1. 全站公共布局**

桌面端采用左侧导航栏 + 顶部导航 + 主内容区。

左侧导航包括：

- 首页
- 常用工具
- 图片工具
- 开发工具
- PDF 工具
- 文本工具
- 数据转换
- 网络工具
- 设计工具
- 办公工具
- 收藏
- 最近使用

导航分类由工具注册表驱动，不要全部硬编码。

移动端使用抽屉式导航。

**2. 首页**

首页包含：

- 品牌名称及简短介绍
- 醒目的全站工具搜索框
- 热门工具快捷入口
- 常用工具区域
- 按分类浏览工具
- 最近更新工具
- 收藏和最近使用入口

首页可以保留适度的品牌视觉区域，但工具查找和使用始终是主要目的。

不需要一次性展示全部工具。

**3. 工具详情页**

工具详情页采用统一页面框架，但每种工具内部可以有独立交互布局。

通用结构：

- 面包屑导航
- 工具名称、图标和描述
- 工具主操作区域
- 使用说明
- 功能特点与常见问题
- 相关工具推荐

不同工具应采用最适合其用途的交互形式。

例如：

- 图片压缩：上传区域、参数设置、原图/压缩图对比、批量下载。
- JSON 格式化：左右分栏编辑器、格式化、校验、错误提示和树形视图。
- PDF 合并：文件拖拽上传、排序、预览及合并下载。
- API 调试：请求配置、Header、Body、响应结果等独立面板。

不要所有工具都使用相同的输入框加按钮模板。

## 四、系统架构

采用模块化工具架构。

每个工具应拥有独立模块，工具信息通过统一注册表管理。

建议目录结构：

```text
src/
├── app/
│   ├── page.tsx
│   ├── tools/
│   │   ├── page.tsx
│   │   └── [slug]/
│   │       └── page.tsx
│   └── categories/
│       └── [slug]/
│           └── page.tsx
├── components/
│   ├── layout/
│   ├── ui/
│   └── tools/
├── tools/
│   ├── image-compress/
│   ├── json-formatter/
│   ├── pdf-merge/
│   └── ...
├── registry/
│   ├── tools.ts
│   └── categories.ts
├── hooks/
├── lib/
└── types/
```

具体目录允许根据 Next.js 最佳实践调整。

### 工具注册机制

每个工具拥有统一的元数据：

- 唯一 ID
- 名称
- 描述
- 分类
- URL Slug
- 图标
- 搜索关键词
- 是否热门
- 是否推荐
- 更新日期
- SEO 元数据

首页、分类导航、搜索、推荐等功能统一使用注册表。

新增工具时，尽量只需增加工具模块及注册配置。

工具的 UI 与业务逻辑分离。

工具组件按需加载，避免所有依赖被打包进首页。

Next.js 静态动态路由应使用 `generateStaticParams()`。

## 五、第一阶段开发范围

第一阶段重点是完成网站基础架构、UI 和三个代表性工具。

### 1. 图片压缩

可研究：

https://github.com/Donaldcwl/browser-image-compression

功能要求：

- 上传图片
- 支持拖拽上传
- 可选择压缩质量或目标大小
- 显示压缩前后文件大小
- 显示压缩率
- 原图与结果预览
- 下载压缩后的文件
- 支持批量操作

### 2. JSON 格式化

可研究：

https://github.com/josdejong/jsoneditor

功能要求：

- JSON 格式化
- JSON 压缩
- JSON 语法校验
- 错误提示及定位
- 树形结构展示
- JSON 文本复制
- JSON 文件导入和导出

### 3. PDF 合并

可研究：

https://github.com/Hopding/pdf-lib

功能要求：

- 上传多个 PDF
- 文件列表展示
- 拖动调整顺序
- 合并 PDF
- 下载结果
- 浏览器本地处理

### 后续规划工具

图片类：图片格式转换、图片尺寸调整、图片裁剪、图片转 Base64、图片加水印。

开发类：JSON Diff、JSON 转 TypeScript、JWT 解码、URL 编解码、时间戳转换、正则测试、UUID、Hash、SQL 格式化。

文本类：文本 Diff、文本去重、批量替换、Markdown 预览。

PDF 类：PDF 拆分、PDF 页面排序、图片转 PDF。

其他：二维码生成、二维码识别、文件批量重命名。

在线 API 调试器放在后续阶段。需要明确浏览器 CORS 限制，不应宣传为支持任意跨域请求。

## 六、SEO 要求

网站需要从一开始考虑 SEO。

- 每个工具使用独立 URL。
- 每个工具拥有独立 title、description、H1。
- 生成 sitemap.xml 和 robots.txt。
- 添加 canonical URL。
- 页面内容使用语义化 HTML。
- 工具页面提供有实际价值的使用说明。
- 支持工具名称、别名和中英文关键词搜索。
- 分类页有可索引的介绍内容。
- 尽可能确保主要内容在静态 HTML 中可获取。
- 优化加载性能与 Core Web Vitals。

不要仅仅依靠 meta keywords 来实现 SEO。

## 七、非功能性要求

### 性能

- 首页不加载所有工具的重量级依赖。
- 大文件处理尽可能使用 Web Worker。
- 按需加载 Monaco、PDF 等模块。
- 合理处理文件大小限制和内存不足。
- 及时释放 Object URL 和其他浏览器资源。

### 隐私

- 默认在客户端本地处理文件。
- 不上传用户文件。
- 不默认保存敏感内容。
- 用户收藏、偏好和最近使用记录可保存在本地。
- 清楚说明不同工具的数据处理方式。

### 可维护性

- 统一代码风格。
- TypeScript 严格类型检查。
- 适度抽象，不要过度设计。
- 优先采用成熟且维护良好的开源库。
- 检查第三方项目许可证，确保满足实际使用及分发要求。
- 工具实现需要方便独立测试。
- 保留后续扩展空间，但不要提前建设复杂插件系统。

## 八、部署要求

代码托管在 GitHub。

使用 GitHub Actions 或 Cloudflare Pages 的 Git 集成自动部署。

Next.js 使用静态导出，生成 `out` 目录。

项目应支持绑定自定义域名并使用 HTTPS。

提供 README，说明：

- 本地开发方法
- 构建命令
- 项目目录结构
- 新增工具的方法
- 静态部署配置
- 环境限制和注意事项

## 九、开发顺序

**Phase 1：项目基础**

初始化 Next.js、TypeScript、Tailwind CSS、shadcn/ui，建立代码规范和目录结构。

**Phase 2：界面搭建**

按照确认的第二版设计图，实现完整首页、全站布局、分类页面和工具详情页的公共框架。

这个阶段先确保 UI 还原度，不要急着开发大量工具。

**Phase 3：工具注册系统**

完成工具注册表、分类、站内搜索、收藏和最近使用功能。

**Phase 4：三个核心工具**

依次完成图片压缩、JSON 格式化、PDF 合并，确保真实可用，而不是演示界面。

**Phase 5：测试与发布**

进行响应式适配、功能测试、性能检查、SEO 检查、静态构建及 Cloudflare Pages 部署验证。

## 十、第一版验收标准

1. 页面符合确认的第二版设计图，视觉统一。
2. 桌面和移动端均可正常使用。
3. 首页搜索与分类导航正常。
4. 三个核心工具功能完整且可用。
5. 收藏及最近使用可以在刷新后保留。
6. 工具可以通过统一注册机制扩展。
7. 页面具备基础 SEO 信息。
8. `pnpm build` 成功生成静态站点。
9. 无需运行后端服务器即可部署和使用。
10. 不存在明显的 TypeScript、Lint 或运行时错误。

## 十一、对 Codex 的执行要求

请首先检查当前仓库，如果是空仓库，从项目初始化开始。

先根据上述需求给出简洁的实施计划，然后按阶段执行。

优先完成基础架构和高质量 UI，接着实现三个核心工具。

不要一次性安装所有未来可能使用的依赖。

不要擅自增加后端、数据库、登录或收费功能。

对于有技术限制的功能，明确说明限制，不要采用不可靠的模拟实现。

设计稿是重要的视觉依据。实现时重点关注布局比例、间距、字体、边框、配色、工具卡片样式及整体视觉一致性。

**最终目标不是完成一个工具导航页面，而是构建一个能够长期维护和扩展、真正好用的在线工具平台。**
